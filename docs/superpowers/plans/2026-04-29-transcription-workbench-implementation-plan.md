# 扒谱工作台实现计划

日期：2026-04-29
关联设计文档：`docs/superpowers/specs/2026-04-29-transcription-workbench-design.md`

## 1. 实现目标

基于设计文档，第一版实现目标如下：

- 做出可替代用户高频 `wavetone` 工作流的桌面端扒谱工具
- 保证原始频谱主工作流先成立
- 在项目制骨架上接通少量高价值 provider
- 让分轨与分析结果统一回挂项目

## 2. 实施原则

- 先完成主频谱工作流，再接入增强能力
- 先保证一个完整垂直切片可用，再扩展功能面
- provider 接口按第一版实际需求设计，不做过度抽象
- 所有扩展能力都不能破坏主频谱观察体验
- 每个阶段都应可运行、可验证、可回退

## 3. 建议里程碑

### Milestone 1: 项目骨架与音频主工作流

目标：

- 建立应用基础架构
- 能导入一个音频项目
- 能显示波形与原始频谱
- 能完成基本播放、定位、调速

交付内容：

- 项目创建与打开流程
- Source Audio 数据模型
- 基础 Workspace State 模型
- 音频加载与缓存机制
- 波形与频谱渲染主界面
- 播放、暂停、拖动、定位、循环、变速不变调

验收标准：

- 可以导入一首曲子并开始做基础扒谱操作
- 主界面即使没有任何 provider，也已经是可用工具

### Milestone 2: 频谱观察增强与节拍对齐

目标：

- 补齐第一版高频 `wavetone` 能力
- 让频谱观察体验达到可迁移水平

交付内容：

- 左右声道视图切换
- 频谱光标的时间线与音高线
- 泛音参考线
- 精确时间定位
- BPM / 拍号 / 时间偏移网格叠加
- EQ 频段处理

验收标准：

- 用户能仅依赖主界面完成主要观察任务
- 节拍网格与音乐重音能手动对齐

### Milestone 3: 项目制管理与工作现场恢复

目标：

- 把“文件查看器”升级为真正的项目工作台

交付内容：

- Derived Audio Assets 模型
- Timeline Annotations 模型
- Analysis Runs 模型
- Provider Artifacts Metadata 索引
- 布局预设与 dock 状态保存
- 项目重开后的现场恢复

验收标准：

- 重新打开项目时能恢复工作区、标记、参数和观察位置
- 派生资产与分析记录可被统一索引

### Milestone 4: Provider 基础设施与首个音频类 provider

目标：

- 跑通统一 provider 流程
- 先接通一个高价值分轨能力

交付内容：

- provider 描述模型
- 统一运行流程 UI
- 本地或远程任务执行器
- 首个 Audio Transform Provider
- 分轨结果自动纳入 Derived Audio Assets
- stem 结果在 dock 中预览和切换

验收标准：

- 从项目内发起一次分轨任务并在项目内拿到可管理结果

### Milestone 5: 首个分析类 provider 与 LLM 分析入口

目标：

- 跑通分析型结果回挂项目
- 验证分析增强层不会打断主工作流

交付内容：

- 首个 Analysis Provider
- 一个 LLM 分析入口位
- 分析结果写入 Analysis Runs
- 结果可在 dock、时间轴或频谱叠加层中查看
- 分析结果与人工标注分开存储

验收标准：

- 对某个困难片段发起分析任务，结果能辅助判断但不破坏主界面体验

### Milestone 6: 打磨、验证与兼容清单

目标：

- 用真实曲目验证第一版
- 收拢体验问题和后续兼容计划

交付内容：

- 高频工作流验证脚本
- 分轨接入验证
- 分析增强验证
- 项目恢复验证
- 低频 `wavetone` 功能兼容清单
- 后续版本优先级列表

验收标准：

- 用户愿意在真实任务中优先使用该工具而不是回退到 `wavetone`

## 4. 技术分层建议

建议按以下分层实现：

### 4.1 Application Shell

负责：

- 窗口与应用生命周期
- 菜单、命令、快捷键
- 项目打开与保存流程

### 4.2 Audio Engine

负责：

- 音频解码
- 播放控制
- 变速不变调
- 声道视图
- EQ 处理

### 4.3 Visualization Engine

负责：

- 波形渲染
- 频谱渲染
- 光标与辅助线
- 节拍网格
- 叠加层绘制

### 4.4 Project Store

负责：

- 项目数据结构
- 资产索引
- 分析记录
- 标记与工作区状态
- 序列化与恢复

### 4.5 Workspace Layout System

负责：

- 主工作区
- dock 管理
- 布局预设
- 用户自定义布局状态

### 4.6 Provider Runtime

负责：

- provider 注册
- 参数校验
- 任务运行
- 结果标准化
- 错误与日志记录

## 5. 推荐开发顺序

推荐按以下顺序推进，而不是按模块平均铺开：

1. 建立最小项目骨架与音频加载
2. 做出主频谱与播放定位闭环
3. 补齐网格、光标、EQ、声道等高频核心能力
4. 加入项目保存与工作现场恢复
5. 接入首个分轨 provider
6. 接入首个分析 provider
7. 接入 LLM 分析入口
8. 最后再做更多布局打磨和兼容清单

## 6. 第一版最小垂直切片

如果要最快验证方向，建议先做以下最小闭环：

- 导入一个项目
- 显示原始频谱
- 播放 / 拖动 / 调速 / 定位
- 手动对齐节拍网格
- 保存一个标记
- 运行一次分轨
- 在项目里看到并管理分轨结果

这个闭环一旦成立，就已经能验证产品方向是否正确。

## 7. 风险控制策略

- 如果频谱渲染性能不足，优先保住主交互流畅度，再优化显示精度
- 如果变速不变调实现复杂，先选择稳定方案，不为“最完美音质”阻塞主流程
- 如果 provider 接入不稳定，先把结果索引、任务记录和失败恢复机制做对
- 如果 LLM 结果质量波动大，先把它限制在可选分析 dock 内，不进入默认主界面

## 8. 计划输出

实现计划完成后，进入开发时建议先创建以下工作项：

- 音频主工作流 P0
- 频谱观察增强 P0
- 项目模型与恢复 P0
- 首个分轨 provider P1
- 首个分析 provider P1
- LLM 分析入口 P1
- 低频 `wavetone` 兼容清单 P2

## 9. 结论

最重要的执行判断是：

- 不要先做“很多 AI”
- 不要先做“很多 provider”
- 不要先做“很多低频兼容”

第一版应当先把“主频谱工作流 + 项目制管理 + 一个可跑通的 provider 流程”做成。

只要这条主线成立，后续分轨、分析和 LLM 扩展都会自然接上。
