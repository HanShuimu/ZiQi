# 扒谱工作台设计文档

日期：2026-04-29

## 1. 产品定义

这是一个以原始频谱为核心观察面、以项目制管理为骨架、以少量高价值 provider 为增强层的扒谱工作台。

第一版目标不是做自动教学工具，也不是做全自动扒谱系统，而是先替代用户高频使用的 `wavetone` 工作流，并在此基础上接入分轨与分析增强能力。

## 2. 设计目标

第一版需要满足以下目标：

- 覆盖用户高频使用的 `wavetone` 核心能力，并提供大致相似的使用体验
- 始终保留未经处理的原始频谱与音频观察能力，作为最高优先级的信息层
- 以“一个项目对应一个源音频”的方式统一管理分轨结果、分析结果、时间轴标记和工作区状态
- 支持统一流程下的 provider 插拔，使本地能力与远程 API 能力都能纳入同一工作流
- 在核心工作流稳定后，优先支持分轨与分析增强能力

## 3. 非目标

第一版明确不做以下方向：

- 低频 `wavetone` 功能的全面兼容
- 教练式引导、分层提示、教学模式
- 大规模 provider 插件市场或复杂扩展生态
- 以自动给出完整答案为目标的全自动扒谱系统
- 多项目协作、云端共享、团队工作流

## 4. 用户与使用场景

目标用户是已经有明确扒谱需求、希望借助专业工具辅助观察和分析的音乐学习者或创作者。

核心使用场景如下：

1. 导入一首完整音频，观察原始频谱与波形
2. 在时间轴上精确定位某一时刻或短句，调整播放速度并循环播放
3. 通过左右声道查看、频谱浏览、泛音参考、EQ 频段处理等方式聚焦目标内容
4. 通过节拍网格与 BPM、拍号、时间偏移设置，将网格与音乐重音对齐
5. 对困难片段运行分轨或分析能力，将结果挂回项目中统一查看
6. 保存标记、观察位置和工作区状态，便于后续继续分析

## 5. 第一版核心能力范围

### 5.1 `wavetone-compatible core`

第一版优先覆盖以下高频核心能力：

- 打开音频并查看频谱
- 拖动当前进度
- 从当前进度播放音频
- 调整播放速度且不变调
- 在时间轴上精确定位某个时间点
- 查看左右声道
- 分析乐曲速度，并通过节拍数、BPM、时间偏移在频谱上对齐网格
- 在频谱界面浏览时间与音高信息
- 显示光标对应的竖线与横线
- 可选显示泛音参考线
- 调整音频 EQ，用于弱化或屏蔽特定频段

### 5.2 增强能力

在核心能力可用后，第一版优先接入以下增强方向：

- 分轨能力
- 分析能力
- LLM 辅助分析入口

增强能力的目标是辅助观察与判断，而不是取代原始观察工作流。

## 6. 信息架构

一个项目只围绕一个源音频展开。

项目包含以下对象：

### 6.1 Source Audio

项目唯一主素材。

包含：

- 原始音频文件
- 时长
- 采样率
- 声道数
- 其他基础元数据

### 6.2 Derived Audio Assets

由源音频派生出的音频资产。

包含但不限于：

- 分轨结果
- 声道拆分结果
- 局部导出音频
- EQ 或其他处理缓存

每个派生资产都必须记录来源信息，例如：

- 来源 provider
- 模型或服务名称
- 运行参数
- 生成时间
- 与源音频或时间范围的关系

### 6.3 Analysis Runs

分析任务的运行记录，而不是只有最终结论。

例如：

- BPM / 节拍分析
- 和弦候选分析
- 音高聚类分析
- 段落边界分析
- LLM 判断结果

每条记录至少保存：

- 输入范围
- 使用的输入资产
- provider 或模型来源
- 参数
- 输出结果
- 时间戳
- 运行状态

### 6.4 Timeline Annotations

挂在时间轴上的人工信息。

包括：

- 标记点
- 循环区间
- 备注
- 疑难片段标记
- 保存的观察位置

人工标注必须与 AI 分析结果分开存储。

### 6.5 Workspace State

界面状态也是项目数据的一部分。

包括：

- 当前布局预设
- dock 打开状态
- 网格参数
- EQ 设置
- 左右声道模式
- 频谱显示参数
- 光标位置
- 视口位置

### 6.6 Provider Artifacts Metadata

provider 相关的原始产物与元信息索引。

包括：

- 输出文件列表
- provider 名称
- 模型版本
- API 响应摘要
- 失败日志
- 文件路径映射

## 7. 主界面与工作区设计

第一版界面采用“主频谱中心 + 可配置 dock 工作区”模式。

### 7.1 核心原则

- 主频谱工作区永远存在
- 原始频谱始终是中心观察面
- 分轨、分析、笔记等能力都作为附加视图停靠
- 附加视图可切换、可展开、可并排、可隐藏
- 默认布局应尽量克制，不能默认摊开所有面板
- 用户可保存自己的布局预设

### 7.2 推荐布局结构

主界面包含：

- 顶部工具栏
- 左侧项目 rail
- 中央主频谱工作区
- 下方或侧边 dock 区
- 底部 transport / 时间导航区

### 7.3 推荐布局预设

至少支持以下预设：

- `Pure Spectrum`
  仅保留主频谱工作区
- `Spectrum + Analysis`
  主频谱加一个分析 dock
- `Wide Compare`
  主频谱加多个并排 dock，用于大屏比较

## 8. Provider 模型

第一版采用“统一流程 + provider 插拔”的能力模型。

### 8.1 Provider 分类

分为两类：

#### Audio Transform Providers

产出新的音频资产。

例如：

- 分轨
- 声道拆分
- 局部导出
- 频段隔离

#### Analysis Providers

产出结构化分析结果。

例如：

- BPM / 节拍推断
- 和弦候选
- 音高聚类
- 段落边界
- LLM 辅助判断

### 8.2 统一运行流程

所有 provider 都走相同工作流：

1. 选择时间范围或整首范围
2. 选择输入资产
3. 选择 provider
4. 配置参数
5. 运行任务
6. 将结果自动挂回项目

### 8.3 Provider 最小能力描述

每个 provider 至少需要声明：

- 类型：`audio transform` 或 `analysis`
- 接受的输入类型
- 输出类型
- 本地或远程运行方式
- 参数模式
- 可追溯元信息

### 8.4 第一版 provider 策略

第一版采用少量 provider、接口一次设计正确的策略。

第一版至少接通：

- 1 个音频类 provider
- 1 个分析类 provider
- 1 个 LLM 分析入口位

不在第一版构建完整插件生态。

## 9. 第一版明确边界

### 9.1 必须做

- `wavetone` 高频核心能力
- 项目制管理
- 可配置主工作区
- 少量但完整接通的 provider
- 结果统一回挂项目

### 9.2 暂不做

- 低频 `wavetone` 功能全面兼容
- 教学模式
- 大规模 provider 生态
- 全自动扒谱定位
- 协作与共享系统

## 10. 风险点

### 10.1 主工作流被扩展能力挤压

如果分轨、LLM、分析面板过重，工具会失去顺手感。

约束：

- 关闭所有扩展能力后，主界面仍然必须是完整可用的扒谱工具

### 10.2 Provider 抽象过重

如果过早为未来能力设计过复杂接口，会拖慢第一版。

约束：

- 只围绕第一版实际接入的少量 provider 设计最小可扩展模型

### 10.3 项目管理退化为文件收纳

如果项目层只存文件，不保存工作现场，就无法体现价值。

约束：

- 项目必须恢复标记、工作区状态和分析运行记录，而不只是恢复文件列表

### 10.4 过早依赖自动分析结论

如果 AI 结果被当作主结论，可信度问题会直接伤害体验。

约束：

- AI 结果始终作为附加层、候选层或参考层出现

## 11. 验证策略

第一版通过以下场景验证：

### 11.1 主工作流替代验证

选择一首真实需要扒谱的曲子，完成以下流程：

- 导入音频
- 浏览频谱
- 定位片段
- 调速播放
- 对齐节拍网格
- 记录标记

验收标准：

- 这套流程的顺手程度不低于当前 `wavetone`

### 11.2 分轨接入验证

对同一项目运行一次分轨 provider。

验收标准：

- 分轨结果被统一纳入项目管理，而不是成为散乱外部文件

### 11.3 分析增强验证

对困难片段运行一次分析或 LLM 辅助。

验收标准：

- 结果能帮助观察和判断
- 不打断主频谱工作流

### 11.4 工作现场恢复验证

间隔一段时间后重新打开项目。

验收标准：

- 能恢复工作区状态、标记、网格参数和分析记录

## 12. 结论

第一版产品定位如下：

“一个以 `wavetone` 高频核心能力为底座、以原始频谱为中心观察面、以项目制管理统一分轨与分析结果、以少量高价值 provider 为增强层的扒谱工作台。”

第一版的成功标准不是功能数量最多，而是：

- 高频工作流能自然迁移
- 主界面足够顺手
- 分轨和分析能力真正融入项目现场
- 后续扩展不会破坏核心观察体验
